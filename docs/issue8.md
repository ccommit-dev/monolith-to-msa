- 모놀리식 아키텍처의 한계점 이해
- MSA 전환 필요성 인식

## 핵심 메시지

### 1. VU 200 병목 현상
- **증상**: 응답 시간 급증, 에러율 증가, 타임아웃 발생
- **원인**: 동시 요청 증가로 인한 리소스 경쟁
- **영향**: 사용자 경험 저하, 시스템 불안정

### 2. 커넥션 풀 고갈
- **HikariCP max 10**: 제한된 커넥션 수
- **증상**: 커넥션 획득 대기 시간 증가
- **결과**: 요청 처리 지연 및 실패

### 3. 모놀리식 아키텍처의 한계
- **단일 데이터베이스**: 모든 서비스가 하나의 DB 공유
- **확장성 제약**: 수직 확장만 가능
- **장애 전파**: 한 서비스의 문제가 전체에 영향

### 4. MSA 전환 필요성
- **독립적 확장**: 서비스별 독립적인 스케일링
- **장애 격리**: 서비스 간 장애 전파 방지
- **리소스 분리**: 서비스별 독립적인 DB 커넥션 풀

## 실습 순서

### 1단계: 환경 설정

#### 1.1 HikariCP 커넥션 풀 설정 확인

**파일 위치:**
```
src/main/resources/application.yaml
```

**설정 내용:**
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10  # 최대 커넥션 수 (병목 재현을 위해 낮게 설정)
      minimum-idle: 5         # 최소 유휴 커넥션 수
      connection-timeout: 30000  # 커넥션 획득 대기 시간 (30초)
      idle-timeout: 600000   # 유휴 커넥션 타임아웃 (10분)
      max-lifetime: 1800000   # 커넥션 최대 생명주기 (30분)
      leak-detection-threshold: 60000  # 커넥션 누수 감지 (60초)
```

**확인:**
```bash
cat src/main/resources/application.yaml | grep -A 10 "hikari:"
```

#### 1.2 Actuator 메트릭 활성화 확인

**설정 확인:**
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    export:
      prometheus:
        enabled: true
```

**메트릭 확인:**
```bash

# 활성 커넥션 수

# 대기 중인 스레드 수

# HTTP 요청 메트릭
curl http://localhost:8080/actuator/metrics/http.server.requests
```

#### 1.3 애플리케이션 실행

```bash

```

**확인:**

- H2 Console 접속 가능한지 확인: `http://localhost:8080/h2-console`

**예상 결과:**
- **TPS**: 50~100 요청/초
- **평균 응답 시간**: 100~300ms
- **95% 응답 시간**: 500ms 이하
- **에러율**: 1% 이하
- **커넥션 풀 사용률**: 50~70% (5~7개 커넥션 사용)

**확인 방법:**
1. **Locust 리포트 확인:**
   - `report_bottleneck_vu100.html` 파일 열기
   - Statistics 탭에서 응답 시간, TPS 확인
   - Failures 탭에서 에러율 확인

2. **Actuator 메트릭 확인:**
   ```bash
   # 커넥션 풀 상태
   curl http://localhost:8080/actuator/metrics/hikari.connections.active | jq '.measurements[0].value'
   
   # 대기 중인 스레드
   curl http://localhost:8080/actuator/metrics/hikari.connections.pending | jq '.measurements[0].value'
   ```

3. **애플리케이션 로그 확인:**
   - 커넥션 풀 관련 경고 메시지 확인
   - 타임아웃 오류 확인

### 4단계: 분석 및 리포트

#### 4.1 병목 지점 분석

**병목 발생 지점:**
1. **커넥션 풀**: HikariCP max 10 커넥션 모두 사용
2. **DB 쿼리**: 비관적 락으로 인한 커넥션 점유 시간 증가
3. **트랜잭션**: 긴 트랜잭션으로 인한 커넥션 보유 시간 증가

**성능 지표 비교:**

| 지표 | VU 100 (정상) | VU 200 (병목) | 변화율 |
|------|---------------|---------------|--------|
| TPS | 50~100 | 20~30 | -70% |
| 평균 응답 시간 | 100~300ms | 1~5초 | +1600% |
| 95% 응답 시간 | 500ms | 10초+ | +1900% |
| 에러율 | <1% | 10~30% | +2900% |
| 커넥션 풀 사용률 | 50~70% | 100% | +43% |

#### 4.2 근본 원인

**1. 제한된 커넥션 풀 크기**
- HikariCP max 10: 동시 처리 가능한 요청 수 제한
- VU 200 요청 시 커넥션 부족 발생

**2. 긴 트랜잭션 시간**
- 비관적 락 (SELECT FOR UPDATE) 사용
- 재고 차감 + 주문 생성 + 결제 처리로 인한 긴 트랜잭션
- 커넥션 점유 시간 증가

**3. 모놀리식 아키텍처의 한계**
- 모든 서비스가 하나의 DB 공유
- 서비스 간 커넥션 경쟁
- 확장성 제약 (수직 확장만 가능)

#### 4.3 리포트 데이터 기반 MSA 분리 필요성 분석

**VU 100 베이스라인 테스트 결과 분석:**

실제 테스트 결과 (`report_bottleneck_vu100.html` 기준):

| 엔드포인트 | 요청 수 | 실패 수 | 실패율 | 평균 응답 | 95% 응답 | 99% 응답 | 최대 응답 |
|-----------|--------|--------|--------|----------|----------|----------|----------|
| POST /api/orders | 5,819 | 1,890 | **32.5%** | **4.13초** | **8초** | **35초** | **297초** |
| POST /api/payments | 23 | 0 | 0% | 1.59초 | 4.2초 | 7.2초 | 7.2초 |
| GET /api/products/[productId] | 1,374 | 0 | 0% | 2.4ms | 5ms | 19ms | 260ms |
| GET /api/products/[productId]/stock | 883 | 0 | 0% | 1.8ms | 4ms | 14ms | 51ms |
| **Aggregated** | **8,099** | **1,890** | **23.3%** | **8.08초** | **8초** | **46초** | **7,194초** |

**핵심 발견 사항:**

1. **주문 서비스의 심각한 성능 저하**
   - 실패율 32.5%: VU 100에서도 이미 높은 실패율
   - 평균 응답 시간 4.13초: 사용자 경험 저하
   - 99% 응답 시간 35초: 극단적인 지연 발생
   - 최대 응답 시간 297초 (약 5분): 타임아웃 수준

2. **서비스별 성능 차이**
   - 상품 조회: 평균 2.4ms (정상)
   - 재고 조회: 평균 1.8ms (정상)
   - 주문 생성: 평균 4.13초 (**1,700배 느림**)
   - 결제 처리: 평균 1.59초 (상대적으로 양호)

3. **리소스 경쟁 현상**
   - 주문 서비스가 커넥션 풀을 장시간 점유
   - 상품 조회 서비스에도 간접적 영향 (전체 평균 8.08초)
   - 단일 커넥션 풀 공유로 인한 서비스 간 간섭

**MSA 분리가 필요한 이유:**

**1. 서비스별 독립적 확장 필요성**
- **현황**: 주문 서비스만 높은 부하 (5,819 요청, 32.5% 실패)
- **문제**: 상품 조회는 정상(1,374 요청, 0% 실패)이지만 주문 서비스 영향으로 전체 성능 저하
- **해결**: 주문 서비스만 독립적으로 확장 가능 (인스턴스 증가, 커넥션 풀 증가)

**2. 장애 격리 필요성**
- **현황**: 주문 서비스 실패율 32.5%가 전체 시스템에 영향
- **문제**: 주문 서비스 장애가 상품 조회까지 간접적 영향 (전체 평균 8.08초)
- **해결**: 서비스 분리로 주문 서비스 장애가 상품 조회에 영향 없음

**3. 리소스 경쟁 해소**
- **현황**: 단일 커넥션 풀(max 10)을 모든 서비스가 공유
- **문제**: 주문 서비스의 긴 트랜잭션(비관적 락)으로 커넥션 장시간 점유
- **해결**: 서비스별 독립적인 커넥션 풀으로 리소스 경쟁 제거

**4. 성능 최적화의 독립성**
- **현황**: 상품 조회는 이미 최적화됨(2.4ms)이지만 주문 서비스 영향으로 전체 성능 저하
- **문제**: 모놀리식에서는 한 서비스의 최적화가 다른 서비스에 제한됨
- **해결**: 서비스별 독립적인 최적화 가능 (주문 서비스: 트랜잭션 최적화, 상품 서비스: 캐시 최적화)

**5. 비즈니스 요구사항 차이**
- **주문 서비스**: 높은 일관성 요구(비관적 락), 긴 트랜잭션 허용
- **상품 서비스**: 높은 가용성 요구, 빠른 응답 시간 필수
- **문제**: 모놀리식에서는 서로 다른 요구사항을 동시에 만족하기 어려움
- **해결**: 서비스별로 다른 아키텍처 패턴 적용 가능

**예상 개선 효과 (MSA 전환 후):**

| 지표 | 현재 (모놀리식) | 예상 (MSA) | 개선율 |
|------|---------------|-----------|--------|
| 주문 서비스 실패율 | 32.5% | <5% | **-85%** |
| 주문 평균 응답 | 4.13초 | <500ms | **-88%** |
| 상품 조회 응답 | 2.4ms | 2.4ms | 유지 |
| 전체 평균 응답 | 8.08초 | <1초 | **-88%** |
| 커넥션 풀 효율 | 100% 사용률 | 서비스별 50~70% | **+30%** |

#### 4.4 해결 방안

**단기 해결책:**
1. **커넥션 풀 크기 증가**
   ```yaml
   spring:
     datasource:
       hikari:
         maximum-pool-size: 50  # 10 → 50으로 증가
   ```
   - **장점**: 빠른 적용 가능
   - **단점**: DB 서버 리소스 부담 증가, 근본적 해결 아님
   - **효과**: 실패율 일시적 감소 가능하나 근본 해결 아님

2. **트랜잭션 시간 단축**
   - 비관적 락 대신 낙관적 락 사용
   - 트랜잭션 범위 최소화
   - **장점**: 커넥션 점유 시간 감소
   - **단점**: 동시성 제어 복잡도 증가, 데이터 일관성 리스크

3. **캐시 활용**
   - 상품 조회 캐시 (이미 적용됨)
   - 재고 조회 캐시 (이미 적용됨)
   - **장점**: DB 부하 감소
   - **단점**: 캐시 일관성 관리 필요, 주문 서비스 성능 개선 효과 제한적

**장기 해결책: MSA 전환 (권장)**
1. **서비스 분리**
   - 상품 서비스: 독립적인 DB 커넥션 풀 (max 20)
   - 주문 서비스: 독립적인 DB 커넥션 풀 (max 30)
   - 결제 서비스: 독립적인 DB 커넥션 풀 (max 20)
   - **효과**: 리소스 경쟁 제거, 서비스별 최적화 가능

2. **독립적 확장**
   - 서비스별 독립적인 스케일링
   - 주문 서비스만 인스턴스 증가 (트래픽 집중)
   - 상품 서비스는 현재 인스턴스 유지
   - **효과**: 비용 효율적 확장, 리소스 낭비 방지

3. **장애 격리**
   - 서비스 간 장애 전파 방지
   - Circuit Breaker 패턴 적용
   - 주문 서비스 장애 시 상품 조회는 정상 동작
   - **효과**: 전체 시스템 가용성 향상

4. **성능 최적화 독립성**
   - 주문 서비스: 트랜잭션 최적화, 비관적 락 유지
   - 상품 서비스: 캐시 최적화, 빠른 응답 시간 유지
   - **효과**: 서비스별 최적의 아키텍처 패턴 적용 가능

## 문제 해결

### 커넥션 풀 상태 확인 안 됨

**원인:** Actuator 메트릭 미활성화

**해결:**
```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
```

### 병목 현상이 재현되지 않음

**원인:** 커넥션 풀 크기가 너무 큼

**해결:**
- `maximum-pool-size: 10` 확인
- VU 수를 더 증가 (300, 400)
- `wait_time`을 더 짧게 설정 (0.1~0.5초)

### 테스트 중 애플리케이션 다운

**원인:** 메모리 부족 또는 커넥션 누수

**해결:**
- JVM 힙 메모리 증가: `-Xmx2g`
- 커넥션 누수 확인: `leak-detection-threshold` 설정
- 애플리케이션 재시작
