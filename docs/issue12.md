## Before vs After 비교

### Before: 모놀리식 아키텍처

| 항목 | 내용 |
|------|------|
| 아키텍처 | 단일 애플리케이션 (모놀리식) |
| 포트 | 8080 (단일) |
| 데이터베이스 | testdb (단일 DB) |
| 커넥션 풀 | max 10 (공유) |
| 통신 방식 | 동기 (직접 호출) |
| 캐싱 | 없음 |
| Circuit Breaker | 없음 |
| 배포 | 단일 JAR 파일 |
| 확장 | 수직 확장만 가능 |

**성능 지표 (베이스라인):**
- TPS: ~95 req/s
- 평균 응답 시간: 8,034ms (8초)
- 주문 서비스 평균 응답: 4,113ms (4.1초)
- 실패율: 23.3%
- 최대 응답 시간: 298,000ms (298초)

**주요 문제점:**
- 커넥션 풀 경쟁 (100% 사용)
- 긴 트랜잭션 시간
- 서비스 간 장애 전파
- 확장성 제약

---

### After: MSA + 개선 사항

| 항목 | 내용 |
|------|------|
| 아키텍처 | MSA (Order Service + Payment Service) |
| 포트 | 8080 (Order), 8081 (Payment) |
| 데이터베이스 | orderdb, paymentdb (분리) |
| 커넥션 풀 | max 20 (서비스별 독립) |
| 통신 방식 | 비동기 (Redis Pub/Sub) |
| 캐싱 | Redis 캐싱 (상품/재고) |
| Circuit Breaker | Resilience4j 적용 |
| 배포 | Docker Compose (독립 배포) |
| 확장 | 수평 확장 가능 |

**성능 지표 (개선 후):**
- TPS: ~380 req/s (**4배 증가**)
- 평균 응답 시간: 11.4ms (**90% 감소**)
- 주문 서비스 평균 응답: 12.8ms (**99.7% 감소**)
- 실패율: 22.0% (유사하지만 실패 응답 속도 개선)
- 최대 응답 시간: 248ms (**99.9% 감소**)

**주요 개선 사항:**
- 독립 DB: 서비스별 독립적인 데이터베이스
- 비동기: Redis Pub/Sub을 통한 이벤트 기반 처리
- 캐싱: Redis를 통한 상품/재고 정보 캐싱
- Circuit Breaker: 장애 격리 및 빠른 실패

## TPS 4배 증가

### 개선 효과

| 지표 | Before | After | 개선율 |
|------|--------|-------|--------|
| **TPS** | ~95 req/s | ~380 req/s | **4배** |
| **평균 응답 시간** | 8,034ms | 11.4ms | **99.9% 감소** |
| **주문 평균 응답** | 4,113ms | 12.8ms | **99.7% 감소** |
| **최대 응답 시간** | 298,000ms | 248ms | **99.9% 감소** |

### TPS 증가 요인

1. **독립 DB**
   - 서비스별 독립적인 커넥션 풀 (max 10 → max 20)
   - 커넥션 경쟁 제거
   - 병렬 처리 능력 향상

2. **비동기 처리**
   - Redis Pub/Sub을 통한 이벤트 기반 처리
   - 주문 생성과 결제 처리 분리
   - Non-blocking 처리로 처리량 증가

3. **캐싱**
   - 상품/재고 정보 Redis 캐싱
   - DB 조회 감소
   - 응답 시간 단축

4. **Circuit Breaker**
   - 장애 시 빠른 실패
   - 리소스 낭비 방지
   - 안정성 향상

## 응답 시간 90% 감소

### 응답 시간 개선 상세

| 지표 | Before | After | 개선 |
|------|--------|-------|------|
| **평균 응답 시간** | 8,034ms | 11.4ms | **-99.9%** |
| **주문 평균 응답** | 4,113ms | 12.8ms | **-99.7%** |
| **95% 응답 시간** | 8ms | 74ms | 일관된 성능 |
| **99% 응답 시간** | 46ms | 130ms | 일관된 성능 |
| **최대 응답 시간** | 298,000ms | 248ms | **-99.9%** |

### 응답 시간 감소 요인

1. **독립 DB**
   - 커넥션 풀 경쟁 제거
   - 대기 시간 감소
   - 트랜잭션 처리 속도 향상

2. **비동기 처리**
   - 주문 생성 즉시 응답 (결제는 비동기)
   - 사용자 대기 시간 제거
   - 전체 처리 시간 단축

3. **캐싱**
   - 상품/재고 조회 시간 단축 (DB → Redis)
   - 반복 조회 성능 향상
   - 네트워크 지연 감소

4. **Circuit Breaker**
   - 장애 시 즉시 실패 응답
   - 타임아웃 대기 시간 제거
   - 빠른 실패로 재시도 가능

## 주요 개선 사항

### 1. 독립 DB (Database per Service)

**Before:**
- 모든 서비스가 하나의 DB 공유
- 커넥션 풀 경쟁 (max 10)
- 서비스 간 영향

**After:**
- 서비스별 독립적인 DB (orderdb, paymentdb)
- 독립적인 커넥션 풀 (max 20)
- 서비스 간 영향 제거

**효과:**
- 커넥션 풀 사용률: 100% → 50~70%
- 대기 시간 감소
- 병렬 처리 능력 향상

---

### 2. 비동기 처리 (Redis Pub/Sub)

**Before:**
- 동기 처리 (주문 생성 → 결제 처리 → 응답)
- 긴 트랜잭션 시간
- 사용자 대기 시간 증가

**After:**
- 비동기 처리 (주문 생성 → 이벤트 발행 → 즉시 응답)
- Redis Pub/Sub을 통한 이벤트 기반 처리
- 결제는 비동기로 처리

**효과:**
- 주문 생성 응답 시간: 4,113ms → 12.8ms
- 사용자 경험 향상
- 처리량 증가

---

### 3. 캐싱 (Redis)

**Before:**
- 모든 조회가 DB 직접 접근
- 반복 조회 시 동일한 DB 쿼리
- 네트워크 지연

**After:**
- 상품/재고 정보 Redis 캐싱
- 캐시 히트 시 DB 조회 생략
- 빠른 응답 시간

**효과:**
- 상품 조회 응답 시간: 2.4ms → <1ms (캐시 히트 시)
- DB 부하 감소
- 확장성 향상

---

### 4. Circuit Breaker (Resilience4j)

**Before:**
- 장애 시 타임아웃까지 대기
- 리소스 낭비
- 장애 전파

**After:**
- Circuit Breaker 패턴 적용
- 장애 시 즉시 실패 응답
- 장애 격리

**효과:**
- 실패 응답 시간 단축
- 리소스 효율성 향상
- 안정성 향상
